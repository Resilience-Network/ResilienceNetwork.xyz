Consensus & Finality

Track 01

A Byzantine fault-tolerant Proof-of-Stake engine with a 2/3+1 stake-weighted quorum. Finality is deterministic: once a block is committed under the quorum rule it does not revert absent a byzantine violation of that rule, which is slashable. Validator votes are Ed25519 signatures bounded by signing watermarks and persisted durable consensus locks, so a restarting or partitioned validator cannot equivocate across a recovery boundary.

Block proposers are selected by secret leader election: each validator privately evaluates an RFC 9381 ECVRF over the current view, and a verifiable claim proves the winner without disclosing the schedule in advance — closing proposer-targeted DoS one slot ahead of time. The winner's VRF output doubles as the block randomness field. Making that beacon unbiasable is an open research track; see Decisions.

Key mechanisms

  • 2/3+1 quorum certificates with deterministic single-slot commitment
  • ECVRF secret leader election with verifiable claims
  • Persisted lock/certificate rules across restarts and partitions
  • Validator locks, signing watermarks and enshrined slashing
  • Transferable validator-specific delegation shares (FR-007)

EVM Execution

Track 02

The execution layer runs Ethereum Virtual Machine bytecode with Cancun-compatible semantics over an Ethereum-style state trie, exposed through a 66-method JSON-RPC surface (web3, net, eth, rsc) so existing tooling — wallets, block explorers, deployment pipelines — can speak to the chain without adapters.

Fees follow an EIP-1559-style model (FR-002): a protocol base fee that adjusts per block and is burned, plus proposer tips bounded by user fee caps. Sponsored transactions (FR-004) let a separate payer carry the fees with its own witness and nonce. A native P-256 precompile (FR-013) brings secp256r1 verification on-chain, enabling WebAuthn-style session keys.

Key mechanisms

  • Cancun-compatible bytecode with metered execution and receipts
  • EIP-1559-style base fee, burn and tip accounting
  • Bounded sponsorship with a separate payer witness
  • P-256 verification precompile and session keys
  • Continuously differentially tested against a reference EVM

Shielded State

Track 03

The privacy layer is a native Orchard integration: deposits, private transfers and withdrawals move value into note commitments verified by recursive zero-knowledge proofs over the Pasta curve cycle (Pallas and Vesta) — no trusted setup ceremony. Nullifiers prevent double-spends without linking spenders to notes; Sinsemilla derives commitments inside the circuits. Shielded actions are verified by consensus itself, not by an external bridge or operator.

Selective disclosure (FR-001) is built in: viewing keys, watch-only import and sync, accounting export, outgoing-viewing-key recovery, and payment receipts. This layer is real but explicitly experimental — see the honest limits below and on the Status page.

Shielded activity requires a native (cgo) build with the Rust cryptography statically linked, an explicit experimental acknowledgment, and a trusted RPC for wallet scanning. Bulk historical sync is hash-bound. Independent external cryptographic qualification remains a release gate.

Key mechanisms

  • Halo 2 Plonkish arithmetization over Pasta curves
  • Sinsemilla note commitments and BLAKE3/Poseidon hashing
  • Nullifier-based double-spend prevention with unlinkability
  • Viewing keys, watch-only sync and accounting export
  • Consensus-verified shielded actions

Authorization & Recovery

Track 04

Accounts are sovereign by construction. Session authorization issues revocable, policy-constrained grants: a session key can do exactly what its policy permits, within budgets, for exactly as long as the grant lasts — and nothing else. Authority is layered (ROOT / DIRECT / SESSION), every grant is consensus-visible, and worst-case work is charged before it begins.

Guardian recovery (FR-012) is enshrined: an opt-in guardian quorum can replace account authority after a delay, without custodians or third-party relayers. Native names (FR-015) provide commit-reveal registration, renewal, transfer, target and reverse resolution on-chain.

Key mechanisms

  • Revocable, policy-constrained session grants with budgets
  • ROOT / DIRECT / SESSION authority layers
  • Opt-in guardian quorums with delayed authority replacement
  • Commit-reveal name registration and reverse resolution
  • P-256 session keys toward WebAuthn composition
