// ARCHITECTURE DECISION RECORDS

Decisions with the reasoning attached.

Protocols are the sum of the trade-offs their teams accept. These records preserve the why behind two consequential design choices — in full, with status, so you can disagree with the argument rather than guess at it. Canonical copies live in docs/decisions/.

Unbiasable Randomness Beacon

ADR-01 · Proposed

STATUS: PROPOSED (THRESHOLD RECONSTRUCTION PROTOTYPE) · DATE: 2026-09-17 · ISSUE #33 · PR #204

Context

Secret leader election replaced the public one-slot-lookahead schedule: each validator privately evaluates an RFC 9381 ECVRF over the view, and the winner's output doubles as the next block's randomness beacon. That closes proposer-targeted denial of service — nobody knows whom to attack in advance — but it leaves the beacon itself biasable.

A byzantine winner sees its own output before publishing. If the outcome is unfavorable, it can simply withhold the block and advance the protocol to a fresh view with a fresh randomness draw. One such retry turns a fair contract-visible coin into a three-quarters coin — cheaply, silently, and without slashing a single signature.

Decision

Contract-visible randomness stays blocked until the beacon is unbiasable. The FR-006 EVM randomness precompile does not ship on a biasable source, because exposing one would enshrine proposer advantage into lotteries, airdrops and fair sampling — bugs that can never be patched out of deployed contracts.

The proposed design is distributed beacon output via threshold reconstruction (Shamir-style sharing among validators), with an adversarial simulation demonstrating that no validator — including the proposer — can bias the output. A prototype with byzantine simulation tests is delivered; consensus wiring is deliberately held back until the design lane settles.

Consequences

  • Contracts get no on-chain randomness until the property is proven, not promised
  • The beacon becomes a consensus-critical component with its own threat surface
  • Governance gains a genuinely fair source for future protocol lotteries

Session Authorization V1

ADR-02 · Candidate

STATUS: CANDIDATE FOR EXECUTABLE VALIDATION — NOT APPROVED FOR PRODUCTION

Context

Session authorization lets an account delegate narrow, revocable powers to ephemeral keys. It is the protocol's answer to key management — the layer where most real-world losses happen — so its consensus rules cannot be informal. The record fixes one unambiguous candidate behavior so that independent implementations, test vectors, benchmarks and audits can all target the same protocol instead of their own interpretation of it.

Decision principles

  • Authorization must be deterministic, bounded, non-programmable, and consensus-visible — no general computation hiding inside a grant
  • No field may acquire meaning from an implementation default — every value is explicit on the wire
  • Consensus parsing accepts exactly one encoding for one value
  • Worst-case work must be chargeable before expensive work begins — no un-metered amplification
  • Root recovery must not depend on an active or honest session — the escape hatch cannot be held hostage by the thing it escapes

Consequences

  • Numeric resource and economic parameters remain candidate network parameters until the validation gates pass
  • A mainnet release must copy accepted values into genesis or upgrade configuration and bind them into the protocol-version commitment
  • Wallets and auditors get a single, testable target for the V1 surface
