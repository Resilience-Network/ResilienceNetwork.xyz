Protocol overview

A transaction crosses seven boundaries between a signature and a finalized receipt. Each boundary has one owner in the implementation and one rule it must never break. The five specification pages that follow go into each one.

§1A transaction's path#

  1. Sign. The client serializes a canonical V2 envelope and signs it, bound to the chain and genesis.
  2. Submit. RPC or gossip decodes it and offers it to the transaction pool.
  3. Admit. Pool checks, repeated on every head change, decide eligibility. Admission is not a promise of inclusion.
  4. Propose. The elected proposer orders candidates and simulates them within block budgets.
  5. Execute. Validators authenticate the proposal and execute the whole block strictly. An invalid transaction invalidates the block; a valid action that fails produces a failed receipt.
  6. Finalize. Validators holding more than two thirds of voting power precommit. The commit persists blocks, receipts, state and validator data together.
  7. Observe. RPC exposes the canonical result. Shielded wallets rebuild their state from authenticated compact blocks.

§2Invariants every change must preserve#

  • Identity is more than a chain ID. Genesis, effective consensus configuration and the protocol commitment together identify a network.
  • Execution is deterministic. Proposer selection never replaces strict execution by every validator.
  • Invalid input never partially commits. A valid transaction that fails follows receipt, fee and nonce rules instead.
  • Safety state survives restarts. Validator locks and signing watermarks persist. Running a duplicate signer or resetting them defeats safety.
  • Consensus changes move together. Encodings, gas schedules, activation rules and state-root commitments are reviewed as one change.
  • Advice is not finality. An RPC simulation, a unit test or a past review result is never evidence of inclusion or of deployment readiness.

§3The protocol commitment#

Protocol rules are pinned in a compiled protocol manifest: domain strings, gas prices, action codes, activation revisions and size limits. The manifest is encoded canonically, with each constant's name next to its value, and hashed with Keccak-256. That hash is written into the genesis header together with the chain ID. Timing and economic parameters, such as slot duration, epoch length, stake and slashing, are bound separately by each node's consensus-configuration commitment, and nodes with different values do not interoperate.

A node refuses a genesis whose commitment differs from the one it was built with. There is no migration between manifest revisions: a semantic change means a coordinated restart from a fresh genesis. The log lists every revision.
